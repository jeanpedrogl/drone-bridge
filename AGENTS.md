# AGENTS.md

This file provides guidance to Codex when working with code in this repository.

## What this is

An Android app (Kotlin, single `app` module) named **Drone Bridge** that is the **phone half** of a
two-part system that connects a **DJI aircraft** (tested on the Mini SE) to a computer. Package:
`io.github.jeanpedrogl.dronebridge`. There is no input or control logic in this repo — that is
whatever program runs on the computer (any ROS2 program), which reaches this phone over a ROS2 rosbridge WebSocket. The contract between the two is
`PROTOCOLO.md`; `MANUAL_DESENVOLVEDOR.md` teaches how to write a computer-side program. This app's only jobs:
forward those commands to the DJI SDK, stream the drone's own camera back (to the phone screen and,
relayed, to the computer) for monitoring, and own the one piece of control that must never depend on
any of that — the panic button.

The DJI Mini SE is only supported by **DJI Mobile SDK v4** (`com.dji:dji-sdk` / `dji-sdk-provided`, currently pinned to `4.18` in `gradle/libs.versions.toml`). **Do not use Mobile SDK v5** — that SDK line only supports enterprise aircraft (Matrice, Mavic 3 Enterprise) and does not recognize the Mini SE.

## Build / run

Use the JDK bundled with Android Studio, not a system JDK — there may be no `java` on `PATH`:

```bash
export JAVA_HOME=/path/to/android-studio/jbr
./gradlew :app:assembleDebug
```

- Toolchain: AGP `9.3.3`, `compileSdk`/`targetSdk` 37, `minSdk` 24, JDK toolchain version 25 (see `gradle/gradle-daemon-jvm.properties`).
- No Kotlin Gradle plugin is declared explicitly — this AGP version compiles Kotlin sources without it. Don't add one unless a build actually requires it.
- Tests: `./gradlew :app:testDebugUnitTest` (JVM unit tests) and `./gradlew :app:connectedDebugAndroidTest` (instrumented, needs a device/emulator). The JVM tests cover `RpcRegistry`, `VideoRelayConfig`, `normalizedAxis` and `DocsCoverageTest` (every registered RPC command must appear, in backticks, in `PROTOCOLO.md` and `MANUAL_DESENVOLVEDOR.md`, and the speed limits / watchdog / video defaults quoted there must match the constants in the code — so adding a `cmd(...)` or changing a limit means updating both docs; the two `.md` files are declared inputs of the test task in `app/build.gradle.kts`, otherwise Gradle would skip the test as up-to-date when only a doc changed); the input mapping lives on the computer side, not here. There is no Python code in this repo any more (the old `exemplos/` folder was removed); the manual's reference `rclpy` program and its `ros2 topic pub` examples were checked by hand against a fake phone that no longer exists in the repo. Computer-side programs must start ROS with `rclpy.init(signal_handler_options=SignalHandlerOptions.NO)`: on Humble the default SIGINT handler invalidates the context before `finally` runs, so disarming silently fails to publish `stick_mode: false` (rule 4 of the manual). Single test: `./gradlew :app:testDebugUnitTest --tests "io.github.jeanpedrogl.dronebridge.RpcRegistryTest"`. No lint/format tooling is configured beyond Android's built-in `./gradlew :app:lint`.
- `AGENTS.md` is a copy of this file for Codex (only the title and the tool name differ). When you change one, mirror the change in the other.
- `README.pt-BR.md` is the Portuguese translation of `README.md`; update both together. `PROTOCOLO.md` and `MANUAL_DESENVOLVEDOR.md` are Portuguese-only.
- `app/src/androidTest` holds only the template `ExampleInstrumentedTest` (package-name check); there are no real instrumented tests, and anything touching the DJI SDK can only be verified on hardware.
- `docs/` and `CLAUDE.local.md` are gitignored (personal notes) — don't expect them in a fresh clone and don't commit them.
- The `release` build type has `optimization { enable = false }` (R8 off) and `app/src/main/keepRules/rules.keep` is still the empty template. If you enable shrinking, expect to need DJI keep rules and test on a device.
- Debug APK lands at `app/build/outputs/apk/debug/app-debug.apk`. It's large (150–200MB) because the DJI SDK bundles native libs (maps, flight-safety DB, media codecs) for multiple ABIs and debug symbols aren't stripped — this is expected, not a bug.
- **Install with Run (▶) in Android Studio or `adb install -r`, never "Apply Changes".** Apply Changes leaves an instrumentation agent and `.overlay` dex in the app's `code_cache`, and the DJI protection layer (`libSdkyclx_clx.so`, loaded by `Helper.install`) then aborts the process on launch with `JNI DETECTED ERROR ... GetObjectField` (the app opens and closes at once). Fix on a debug build: `adb shell run-as io.github.jeanpedrogl.dronebridge rm -rf code_cache/startup_agents code_cache/.overlay code_cache/.studio`.

## DJI SDK integration — non-obvious pitfalls

- **`Helper.install()` package**: most DJI tutorials/docs show `com.secneo.sdk.Helper`. In `dji-sdk-4.18.aar` that package is empty and the class lives at **`com.cySdkyc.clx.Helper`** (verified by inspecting the AAR). If bumping the SDK version, re-check this class still resolves before assuming a "missing symbol" error means something else.
- Dependency resolution: `com.dji:dji-sdk` and `com.dji:dji-sdk-provided` resolve straight from **Maven Central** for v4 — no extra DJI-hosted repository needed (unlike v5, which needs `https://developer.dji.com/maven2`).
- `dji-sdk` is `implementation`, `dji-sdk-provided` is `compileOnly` (provided at runtime by the DJI app environment/class loader after `Helper.install()`).
- `app/build.gradle.kts` sets `ndk.abiFilters` to `armeabi-v7a` + `arm64-v8a` only — DJI's own sample excludes `x86` because of a known FFmpeg crash on Android 6+ running on x86.
- `packaging.jniLibs.keepDebugSymbols` and the `META-INF` exclude list in `app/build.gradle.kts` exist because the DJI AAR ships native libs and duplicate `META-INF` entries (e.g. `rxjava.properties`) that otherwise break packaging.
- The DJI **App Key** is generated at https://developer.dji.com/user/apps/, registered under the exact `applicationId` (`io.github.jeanpedrogl.dronebridge`) and signed with the keystore used to build. Without a valid key, `DJISDKManager` registration fails.
- **Secrets:** personal values (the App Key) live in `secrets.properties` at the project root (gitignored, and denied to the agent via `.claude/settings.json` — never read, edit or print it). `app/build.gradle.kts` loads it and injects `DJI_API_KEY` into the manifest through `manifestPlaceholders`; the manifest's `com.dji.sdk.API_KEY` meta-data is `${DJI_API_KEY}`. `secrets.properties.example` is the committed template. To add a new secret: add it to both files, then expose it via `manifestPlaceholders` or `buildConfigField`.
- `VideoFeeder` and `DJICodecManager` (used by `DroneVideoFeed`) live in `dji.sdk.camera` and `dji.sdk.codec` respectively — confirmed by decompiling `dji-sdk-provided-4.18.jar` directly (its bundled "sources" jar is actually empty, so `javap` on the real classes is the only way to get accurate signatures for this SDK; don't trust the method/package names from older public DJI sample code without checking). `DJICodecManager`'s useful constructor for a `TextureView` is `(Context, SurfaceTexture, width, height)`.
- `app/build.gradle.kts` excludes `com.squareup.okhttp3` from the `dji-sdk` dependency (the AAR ships a shaded copy under `dji.thirdparty.okhttp3`, not the real group, so this exclude is about avoiding an unrelated version conflict, not about that shaded copy) — this is why `RosBridgeClient` can add its own plain `okhttp` dependency without any clash.

## Architecture

- `DroneApplication` (`Application` subclass, wired via `android:name` in the manifest): calls `com.cySdkyc.clx.Helper.install(this)` in `attachBaseContext` — this must run before anything touches DJI SDK classes.
- `MainActivity`: requests the runtime permissions the SDK needs (location, Bluetooth, phone state, audio), then calls `DJISDKManager.getInstance().registerApp(...)`. On successful registration it calls `startConnectionToProduct()` and forwards connection events to `DroneController`. It is also the `DroneController.Listener` **and** `RosBridgeClient.Listener`, and owns all UI state (buttons, the status/connection/telemetry text lines at the top). It also runs two independent `Handler` loops: one relays a downscaled JPEG of the drone video to the computer (rate/width/quality from `VideoRelayConfig`; the frame is read already scaled on the main thread, but JPEG + base64 run on a single-thread executor so the 50 ms stick loop is never starved, and a frame is dropped when `RosBridgeClient.pendingBytes()` is over `VIDEO_MAX_BACKLOG_BYTES` or the previous one is still encoding), the other publishes a JSON telemetry blob at 2 Hz — both are no-ops while the bridge is disconnected. `onResume`/`onPause` tell `DroneController` whether the app is in the foreground. Fullscreen immersive, `sensorLandscape` (both landscape orientations); the activity declares `configChanges` so flipping 180° doesn't recreate it, and the root view's insets listener (system bars + display cutout) re-pads on each flip.
- `DroneController`: the only class that touches `FlightController`. Streams virtual stick data every 50 ms while stick mode is on (velocity control, BODY frame, speed caps as constants at the top of the file), plus `takeOff()`, `land()` (also confirms landing when the SDK asks), and `panic()`. Stick values come from `setVelocityCommand(forward, right, up, yawRate)` — the only input source; there is no on-screen joystick. A full-scale (±1) command maps to the caps at the top of the file: 4 m/s horizontal, 2 m/s vertical, 85 °/s yaw (the SDK accepts at most ±100), and the gimbal at 50 °/s. Velocity/gimbal inputs go through `normalizedAxis` (clamped to ±1, NaN → 0), and the watchdogs use `SystemClock.elapsedRealtime()` so a wall-clock change can't stall them. If 500 ms (`COMMAND_TIMEOUT_MS`) pass without a fresh `setVelocityCommand()` call while stick mode is on (Wi-Fi to the computer dropped, the computer program crashed, whatever), the stick loop zeroes the sticks itself and keeps hovering — this is a second, independent safety net below the ROS2 layer, not a replacement for it. `panic()` zeroes the sticks, leaves virtual stick mode (aircraft brakes and hovers, physical RC takes over) and cancels takeoff/landing/go-home; it deliberately does not cut motors, and **panic is never routed through the bridge** — the button calls `DroneController` directly, so it keeps working even if the computer or the Wi-Fi link to it is gone. Stick mode is opt-in (default off): normally armed by the computer publishing `/drone/stick_mode` (`true`), but the phone's own "ASSUMIR CONTROLE (RC)" button can always force it off locally, handing control back to the physical RC sticks regardless of what the computer is doing. `onAppPaused()` turns stick mode off when the app loses the foreground, and `setStickMode(true)` is refused until `onAppResumed()` (the computer must not be able to arm while the pilot can't see the panic button). A failed enable goes through `disableStickMode` (so a repeated `true` that fails while the mode is on can't leave the loop steering with the UI saying "off"), and a successful one does not reset the watchdog clock. `stickWanted` (set by an enable request, cleared by any disable/panic/detach) decides what a late "enable" reply does: undo itself after a panic, but let two enables in a row both stand; the stick loop is always re-posted after `removeCallbacks`, so repeated `true` never doubles the send rate. Known gap: the computer can re-arm right after a panic, and nothing hands control back to the RC automatically after the watchdog hovers the aircraft — only the phone buttons do. Public methods and `Listener` callbacks are main-thread; SDK callbacks are posted to main.
- **`FlightControlData` pitch/roll are swapped vs. their names** (official DJI docs: pitch = velocity along the Y axis, roll = along X; BODY frame is X forward, Y right). So `setVelocityCommand`'s `right` feeds `pitch` and its `forward` feeds `roll`.
- `RosBridgeClient`: a from-scratch, minimal rosbridge v2.0 (JSON-over-WebSocket) client built on OkHttp — **not** a native ROS2 client, because there isn't one for Android (no `rclpy`/`rclcpp`). It auto-reconnects (fixed 3 s backoff) and re-subscribes everything on every reconnect; `connect()` returns false on an invalid address instead of letting OkHttp throw (`MainActivity` shows a toast and doesn't save it — a bad saved address used to crash every launch), `onClosing` closes our side so a graceful server close still triggers the reconnect, and callbacks from a socket that is no longer the current one are ignored (otherwise `connect()` with a new address made the old socket's late close flip the live one to "down" and open a duplicate connection that handled every message twice). It's deliberately generic (`subscribe(topic, type, onMessage)` / `publish(topic, type, JSONObject)`) — all the message-shape-specific parsing (e.g. turning a `geometry_msgs/Twist` JSON blob into a `setVelocityCommand` call) lives in `MainActivity`, not here, so adding a new topic never means touching this class.
  - The computer side's axis convention is ROS-standard **REP 103** (x=forward, y=left, z=up, yaw+=counter-clockwise). `MainActivity.subscribeToCommandTopics()` is where that gets converted to whatever the DJI SDK actually wants — currently `right = -y` (REP103 left-positive → DJI right-positive) and `yawRate = -angular.z`, the latter on the **unverified assumption** that the DJI SDK treats clockwise as positive yaw (the opposite of REP103). Flip the sign there first if the aircraft yaws the wrong way in testing.
  - ROS2 (not ROS1) `std_msgs/Header` field names are `stamp: {sec, nanosec}` — **not** ROS1's `secs`/`nsecs`. `publishVideoFrame()` builds this by hand; getting the field names wrong fails silently-ish (rosbridge just drops/zeroes the field) rather than throwing, so it's easy to miss if copying ROS1-era examples.
  - `sensor_msgs/CompressedImage.data` is base64 in the rosbridge JSON wire format (`Base64.encodeToString(jpeg, Base64.NO_WRAP)`); rosbridge decodes it back to real bytes before it reaches any genuine ROS2 subscriber on the computer.
- **Generic computer access (RPC).** Beyond the fast-path topics (`/drone/cmd_vel`, `/drone/gimbal_pitch_rate`, `/drone/stick_mode`), the computer can run named commands over `/drone/rpc/request` → `/phone/rpc/response` (JSON in `std_msgs/String`; full reference for the computer side in `PROTOCOLO.md`; `MANUAL_DESENVOLVEDOR.md` is the guide for writing computer-side programs, with `ros2 topic pub` examples for every topic and command and a reference `rclpy` program). `RpcRegistry` is the name→command table (id echo, `confirm` guard, 10 s timeout, one-shot `RpcReply`, built-in `system.ping/commands/probe`); it is Android-free apart from `org.json`, so it has JVM unit tests (`RpcRegistryTest`, which needs the real `org.json` as a `testImplementation`). `DroneCommands` registers the actual commands (takeoff/land, `flight.cancel_land_or_rth` — cancels a landing or a return to home, whichever is running, picked from the flight state, and never the takeoff — flight settings, return to home, gimbal, camera mode/photo/record, state, `video.set_quality`/`video.get` backed by `VideoRelayConfig` — fps/max width/JPEG quality of the relayed video, changeable in flight) — to expose something new add one `cmd(...)`/`flightCmd(...)` line there and document it in `PROTOCOLO.md` and `MANUAL_DESENVOLVEDOR.md` (`DocsCoverageTest` fails until both mention it). `DeviceStates` keeps the latest flight/gimbal/camera/battery/RC state objects (`DroneController` feeds flight+battery, `DeviceStates.attach()` hooks the rest) and serializes them on request only (`state.get`, or `state.stream_start` → `StateStreamer` → `/phone/state`, stopped when the bridge disconnects): nothing is pushed unless the computer asks. Deliberately **not** exposed: panic, motors on/off, reboot, calibrations, camera exposure settings, SD formatting, missions, media download.
- **The Mini SE gimbal only accepts pitch** (−90…0°, up to +20° with the range extension); roll/yaw are auto-stabilized and the SDK does not reject commands for them up front. Which commands/getters this aircraft really answers is unverified until run on hardware: `system.probe` and `gimbal.capabilities` report it at runtime. Computer-side programs must not rely on anything here without checking that.
- `DroneVideoFeed`: `VideoFeeder.getInstance().primaryVideoFeed` → `DJICodecManager` decoding into a `TextureView`. Pure monitoring; nothing here feeds back into flight control. `currentFrameBitmap(maxWidth)` (`TextureView.getBitmap(width, height)`, scaled while reading the texture) backs the video relay to the computer.
- Manual override is the physical DJI RC (via "ASSUMIR CONTROLE (RC)", see above), not a touchscreen control.
- Hardware status: the bridge has been run against a real Mini SE (stick mode, takeoff, landing, gimbal and yaw speeds). Still unconfirmed: the yaw-sign assumption above, and which `flight.*`/`gimbal.*` getters this aircraft answers (`system.probe` reports it). For a new test setup: props off with stick mode off (commands reach the phone — check with `ros2 topic echo /drone/cmd_vel` — but never reach `sendVirtualStickFlightControlData`; the app does not log them), then props off with stick mode on, then prop guards, low and in an open area.
